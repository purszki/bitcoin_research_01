1. HIERARCHICAL BLOCK FILTERS (GCS-based)
================================================================================

Approach: Multi-level GCS filters over windows of blocks. L0 covers a window
of N blocks; if L0 matches, fall through to per-block L1 filters.

Results (mainnet 1k blocks, HIER_WINDOW=32, P=12, M=1024):
  - Balanced scenario:       1.5x speedup over per-block GCS
  - Negative-heavy scenario: 2.6x speedup
  - Positive-heavy scenario: 1.3x speedup
  - Strict negative:         3.5x speedup
  - Overall geometric mean:  2.1x speedup

Results (testnet 50k blocks):
  - Overall geometric mean:  5.4x speedup

Conclusion: Moderate improvement, best for negative-heavy workloads.
Still O(N) Golomb decode per filter query.

2. BINARY FUSE16 FILTER (alternative to GCS)
================================================================================

Approach: Replace GCS (BIP 158) with Binary Fuse16 filters from the
xor_singleheader library. Same SipHash-2-4 keying as BIP 158.

Properties:
  - FPR: 1/65536 (~0.0015%) — same order as GCS (1/784931)
  - Query: O(1) per element (3 array lookups + XOR) vs O(N) Golomb decode
  - Size: ~20 bits/element (slightly smaller than GCS ~21 bits/element)
  - Construction: probabilistic hypergraph peeling, deterministic via
    per-block seed derivation from SipHash

Implementation:
  - src/fuse16filter.h / .cpp — C++ wrapper around C library
  - src/crypto/binaryfusefilter.h — C library with added seeded populate
  - Opaque C struct storage (no C header in public .h)
  - Safe deserialization with exact buffer size validation

Ground truth verification:
  - 1k blocks:  21 true hits, 0 false negatives, 0 false positives
  - 20k blocks: 301 true hits, 0 false negatives, 4 false positives
  - Zero construction failures at both 1k and 20k

Benchmark results (client-side: deserialize + MatchAny, 24 wallet scripts):

  1k blocks:

Network cost analysis (Fuse16 vs GCS, 50k blocks):
  - Fuse16 saves ~16 MB in filter data (956 vs 972 MB)
  - 12 false positives cause ~18 MB extra block downloads
  - Net: roughly equivalent network cost, 74x faster queries

Network cost analysis (Fuse16 vs GCS, 20k blocks):
  - Fuse16 saves ~7 MB in filter data (397 vs 404 MB)
  - 3 extra false positives cause ~4.5 MB extra block downloads
  - Net: roughly equivalent network cost, 77x faster queries

Demo executable:
  - src/bench/filter_demo.cpp — self-contained comparison with hardcoded
    real mainnet block data. No external dataset files needed.
  - Build: cmake --build build-release --target filter_demo
  - Run:   ./build-release/bin/filter_demo

Key observations:
  - Speedup inversely proportional to script count: 73x (24 scripts) → 8x (480)
  - GCS query time ~constant (O(N) Golomb decode dominates, script count irrelevant)
  - Fuse16 query time scales linearly with scripts (O(1) per script per filter)
  - FP count scales linearly with scripts (~0.3 FP per script per 50k blocks)
  - Filter sizes identical across wallets (filters are per-block, wallet-independent)
  - Realistic mobile wallets (24-100 scripts): 27-73x speedup, <70 FP
